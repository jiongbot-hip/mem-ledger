# 开发手册

给要改这套代码的人看。README 讲它是什么，这里讲它为什么长这样、改哪里、怎么验。

## 1. 模块地图

```
cli.py                 命令行入口。只做参数解析与打印，逻辑都在 memlib 里
memlib/
  config.py            读 config.toml。所有路径与参数的唯一来源
  schema.py            claim 数据契约：字段、id 派生、日期归一、validate
  text.py              中文句子到结构化事实：别名归一、derive、值归一
  scope.py             可见性判定。private / shared / team: / global
  redact.py            只负责找到唯一那份脱敏规则，不实现规则
  _memredact.py        发行版自带的脱敏规则表（可被覆盖）
  store.py             账本读写、裁决应用、跨源互证、缺口与冲突、取代链
  build.py             构建：跑导入器 -> 去重 -> 裁决 -> 互证 -> 身份 -> 落盘
  search.py            检索：门控 -> BM25 -> 实体门 -> 重排 -> 合并 -> top-k
  atomic.py            原子落盘（唯一临时名 + fsync + replace）
  report.py            冲突报告、端口索引、路径体检、TTL 与探活两节
  ttl.py               按谓词类型算复核日
  dream.py             从冲突生成整合提案（只写 proposals，不写 overrides）
  api.py               只读 HTTP 接口
  selftest.py          内置自检
  importers/           导入器。协议见 importers/__init__.py
tests/test_smoke.py    端到端测试
```

依赖方向是单向的：`schema` / `text` / `scope` 不依赖任何上层，
`store` 依赖它们，`build` / `search` / `report` 依赖 `store`，`cli` 依赖一切。
新代码不要反向依赖。

## 2. 构建的五个阶段，以及顺序为什么不能换

```
1. 导入        每个导入器只读外部来源，产出候选 claim，不写账本
2. 去重        同 id 只留一条
3. 裁决        应用 overrides.jsonl
4. 跨源互证    同一 subject+predicate+value 出现在 >=2 个独立来源 -> proposed 升 verified
5. 身份标注    补 agent_id / visibility / source_session_ids
6. 复核日      按 [ttl] 算 revalidate_after
7. 分片排除    已被归档的条目不进主账本（状态变过的要回来）
8. 排序落盘    scope, subject, predicate, id 排序后原子替换
```

第 3 步必须在第 4 步之前。把人的裁决放在互证之后，人判过的条目会被"自动升格"
再改一遍状态，那是账本和人的裁决打架，而且人永远看不到。

第 7 步只按"状态没变"排除。归档后又被裁决重新打开的（rejected 变回 verified）
必须回到主账本，否则人的裁决被一次归档静默吃掉。

## 3. 写路径唯一提交者

导入器产出候选，`store` / `build` 统一落盘。这条是硬约束，别在导入器里 `open(..., "w")`。

理由：去重、互证、身份标注都要看全局。一个导入器自己写盘，就绕过了所有跨条目的一致性检查，
而且下一次 build 会把它覆盖掉，症状是"改了没效果"。

## 4. 原子落盘与并发

`memlib/atomic.py`。所有账本写入都走它：唯一临时名（`mkstemp`）、`fsync`、
`os.replace`。

不要退回固定 `.tmp` 名。两个 build 并发时它们会写同一个临时文件，
后启动的覆盖前一个写到一半的内容，最后 replace 出来的是混合账本。
测试 `TestAtomic` 用四个进程各写 200 到 5000 行、跑十轮来守这条。

这里刻意不加全局互斥锁。唯一临时名不阻止"后写完的覆盖先写完的"，
但 build 幂等、输入是同一批来源，谁赢都对。加锁会让定时任务和手工命令互相等待，
那是部署策略（外层 `flock`）的事，不是库的职责。

`overrides.jsonl` 用追加模式，不读改写。并发写者用读改写会丢行。

## 5. 失败语义

这个库在几个地方刻意 fail closed，改之前想清楚：

配置缺项直接抛 `ConfigError`，不给默认值。默认值漂了没人会发现，
而它影响的是每一次检索。报错里带 `config.example.toml` 的复制命令。

脱敏规则找不到就拒绝构建账本。少几条规则也能跑，正是 bug 藏进去的方式。

可见性字段缺失按拒绝处理。`rule_as_doc()` 必须显式写 `visibility: "shared"`，
否则规矩层会被作用域闸门整层吃掉。

只读接口拒绝绑定 `0.0.0.0`。要对外请在前面放带认证的反向代理。

`api` 的身份校验：token 缺失、agent 不在表里、服务不通，一律报错，不返回空结果。
空结果会被调用方当成"账本里确实没有"。

## 6. 脱敏：单点

规则只有一份。`redact.py` 按顺序找：`config.toml` 里 `paths.workspace/scripts/_memredact.py`，
然后是包内的 `memlib/_memredact.py`。

`_PATTERNS` 和 `_REPLACEMENTS` 必须等长。`zip` 遇到长短不一致会静默截断，
后面所有规则一起错位。

加规则要有负向用例。已经踩过的：URL 里的 `token=xxx`、`Authorization: Bearer xxx`、
`--token xxx` 三类命令行形态漏了，一条真实连接 token 原样落盘。
但也不能收紧到误伤 `max_tokens=4096` 这种配置文本。

## 7. 改检索参数之前

只有一条规矩：在调参集上试出来的提升不算证据。

具体做法：

1. 建一份问题集，每题要有唯一正确答案的 id。
2. 随机切成调参集和留出集，切法锁死（哈希分层），事后不许重切。
3. 改动前后各跑一遍，逐题比较名次。任何一题名次变差就不能收。
4. 再加一份验证集，只在一个版本定稿时看一次。

原实现里有一道 `gate.py` 做逐题比对和基线锁定。它绑死在原作者那 58 题上，
所以没有随这个发行版发布。你要照上面四步写自己的，别直接复用别人的题。

名词解释，避免搞混：

调参集，用来试的。它的结果永远不能当验收证据。
留出集，用来验收的。跑一次就"脏"一次，跑多了就没意义了。
验证集，最后看一次的。看第二遍它就变成调参集了。

调权重之前先查语料变了什么。原作者的闸门红过一次，三题各掉一名，
最后查出来是那天新建了一个定时器、一份文档复述了某条规矩，
把正确答案挤下去了，检索代码一行没动。先定位内容变化，再决定动不动参数。

## 8. 加一个导入器

协议：

```python
NAME = "my_source"                     # 与 [importers.my_source] 对应
def run(cfg):                          # 返回 (rows, stat)
    ...
    return rows, {"total": 100, "imported": 42}
```

`rows` 里每条是 `schema.make_claim(...)` 的产物。`stat` 至少要含 `total` 和 `imported`，
`build` 会把它们打出来，这是你唯一能看见"这个来源今天导了多少"的地方。

放在 `memlib/importers/` 下会被自动发现（模块级有 `NAME` 和 `run` 就算），
不用改注册表。放包外就设 `importers.dir`。

### 三个容易踩的坑

一、判据不要读自己上一轮的产物。
如果靠"账本里提到过 X"决定收什么，第一次导入后账本里就有了 X，
下一轮它会证明自己该被导入。清单只增不减。做法：读判据时跳过来自本导入器的条目。

二、每条都要有可定位的出处。
`source_refs` 里至少有一个 `path` / `id` / `session` / `at`。没有出处的条目进不了检索
（噪声门会挡掉），也会进"无出处"缺口清单。

三、日期不能兜底成今天。
读不到日期就留空，表示"日期不明"。兜底成今天等于让每次构建把时钟归零，
过一个月所有条目都显示成最新。

## 9. 加断言的地方

自检在 `memlib/selftest.py`。加断言时记住两条：

反例比正例重要。同义词合并错一次、可见性放行错一次都不会当场报错，
只会悄悄把结果弄脏。凡是"不该发生"的，单独写一条。

一条永远为真的断言等于没写。空目录上的"黑名单前缀没写错"恒真，
那不是通过。配置里没有这套来源时，用 `skip()` 标出来，不要让它空过。

## 10. 已知缺口

这些是设计上留着的，不是待修的 bug：

可见性没有区分度。所有导入来源都产出 `shared`，`private` 一条都没有。
作用域闸门代码是通的，但存量数据没有区分度。要闭合得让写入端真的产出
`private` / `team:*`，而改写入端会影响检索结果，必须先过评测闸门。

写回没做。别的框架学到的东西只能留在自己库里，等下一次该库的导入器跑。
这是刻意的：账本只由 build 写，框架只能读、只能 propose。

没有 embedding。核心理由是把"为什么这条排第一"保持成可查可复现的东西。

没有多用户。身份靠 token 映射，没有账号体系。
管理员身份是 `memlib/scope.py` 里的 `MEMORY_ADMIN = "me"`，写死一处。
要换名字就改那一行（它被刻意只留一个定义，`visible()` 读路径和写路径共用）。
没做成配置项，是因为 `visible()` 是个纯函数，把它改成读配置要动 search / store / api
三处的调用链，收益配不上风险。

`team:<名>` 的可见性代码支持，但没有产出团队条目的写入端，所以实际上没人这么用。

## 11. 发版前检查

```bash
python3 -m unittest discover -s tests -v     # 端到端
python3 cli.py self-test                     # 内置自检，看跳过项是不是都是预期的
git status --short                           # 确认没有把 config.toml / *.jsonl 带上
```

`.gitignore` 里排掉了 `config.toml` 和所有 `*.jsonl`。
账本内容是使用者的知识库，一旦推上公开仓库就是数据泄露，不是不整洁。

如果你在本机同时跑着一个改造过的版本，不要两边各改一份。
挑一边当源，另一边用 `rsync` 或子模块同步，否则两份会在细节上慢慢分叉，
而分叉的地方通常是没人测的分支。
